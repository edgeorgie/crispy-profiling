The loop

    
Find → explain → fix → verify

    
Every finding carries its fix. Every fix becomes a test that keeps it fixed.

    

      
1
Find
npx crispy scan detects Vite/Next.js, starts your dev server, visits routes and tries the safe interactions: buttons, tabs, inputs, links. Never anything named delete, pay, submit…

      
2
Explain
Each render is classified: props, state, context or parent. Avoidable ones get a root cause: a recreated callback, an inline object, a context value rebuilt on every render.

      
3
Fix
The report points at src/App.tsx:222 (App) and says what to do: useCallback, useMemo, hoist, React.memo. Agents apply it through the MCP server.

      
4
Verify
npx crispy test records crispy.snap.json. In CI the GitHub Action fails the PR that adds renders and comments the cause and the fix.

How it works

    
The same hook React DevTools uses. No instrumentation in your code.

    

      

        
1
Open the app in headless Chromium
playwright-core drives a real browser. crispy starts your dev server (webServer) or attaches to a running URL. Everything is read-only: non-GET requests and WebSocket messages never leave the browser.

        
2
Record every render
A small hook registers as __REACT_DEVTOOLS_GLOBAL_HOOK__ before React loads and sees each commit: which fibers rendered, with which props, state and context.

        
3
Classify and settle
Per scenario step (click, fill, press, navigate, expect), renders are grouped by phase and compared with the previous props to decide: changed, shallow-equal, recreated callback, context, parent.

        
4
Deterministic report
Sorted, timestamp-free JSON that only changes when your code changes. Budgets, baseline comparison, Markdown for PR comments, and snapshots for crispy test.

      

      

    

  






  

    
Integrations

    
One tool, four doors.

    
Use it from your terminal, from CI, or let your coding agent measure its own fix instead of guessing.

    

      
      
      
      
    


    

      
From your terminal
    
        
  • scan finds and profiles interactions with zero config and writes crispy.config.json.
    • 
        
  • run prints every component with its causes and the fix for a one-off look.
    • 
        
  • test records or checks crispy.snap.json; --ci fails on regressions.
    • 
        
  • compare diffs two reports with a threshold. Exit codes: 0 ok · 1 regression · 2 usage.
    • 
      

      
# install once
npm i -D crispy-profiling
npx crispy install        # Chromium, or set CRISPY_CHROMIUM_PATH

# zero config: find, profile, explain
npx crispy scan

# record the snapshot, commit it, guard the flows
npx crispy test
npx crispy test --ci       # fails when a component adds renders

# one-off deep look at a flow
npx crispy run -s search --markdown report.md

    


    

      
In every pull request
    
        
  • Installs Chromium and its libraries itself: no browser setup in the workflow.
    • 
        
  • Fails when any component renders more than the committed snapshot allows.
    • 
        
  • One PR comment, updated on every push, with the cause, where it renders and the fix.
    • 
        
  • scenarios input splits a slow suite across a job matrix.
    • 
      

      
name: crispy
on: pull_request
permissions: { contents: read, pull-requests: write }
jobs:
  renders:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - uses: edgeorgie/crispy-profiling@v0   # starts your dev server, runs crispy test --ci

Deterministic by design
Sorted output, no timestamps, wall-clock data only behind timings. Two reports of the same scenario differ only when the code changed.

      
Read-only by default
Requests other than GET and WebSocket messages the page sends are blocked in the browser. An interaction that tried to write is reported and not saved.

      
Status: early (0.x)
Improving every week. Bug reports, wrong hints and case studies are the most valuable contribution right now.

    

  






  

    
FAQ

    
Questions people ask first

    
How is this different from React DevTools or why-did-you-render?
Those run in your browser while you look. crispy runs headless, on demand, from the CLI, CI or an agent, and produces a reproducible report with the fix attached. It uses the same DevTools hook, so no code changes are needed, and the numbers are stable enough to snapshot and diff across commits.

    
Does it need changes in my app?
No. It injects the DevTools hook before React loads in headless Chromium. Point it at a development or preview build (dev builds expose component names; production builds work with source maps for original names).

    
Which React versions?
Tested on React 19, validated on 18.3 and 19.0 apps. React 16.8–17 expose the same hook but are not tested.

    
Will it click "delete" in my app?
No. scan only tries safe interactions and skips anything named delete, pay, sign out, submit… in several languages. Every command is read-only: writes never leave the browser unless you pass --allow-writes.

    
Is a render count really stable in CI?
Per-component render counts are reproducible for the same code. Commit counts and effect cascades can vary with load timing, so snapshots store them as ranges. Timings (ms) are informative, never the gate.

    
What does it cost?
MIT licensed, free. About 20–25 s per scenario per CI run on a GitHub runner, plus one minute to install Chromium. Split scenarios across a job matrix when it grows.
